# Changelog

One entry for each merge into `master` that changes the code. Each entry says if a file under `results/` changes.
The tool versions of a run are in its `results/summary/run_info.txt`; cite those. Before this file, the merges are in `git log --merges`.

## Unreleased
- Rules `signalp_parallel` and `targetp_parallel` no longer depend on the CPU count of the job. `signalp_parallel` sets `OMP_NUM_THREADS` and `MKL_NUM_THREADS` to `threads` (1); PyTorch reads them, and SignalP 6.0g in `signalp.sif` sets no thread count and has no thread option. `targetp_parallel` runs TargetP under `taskset -c` on the first `threads` CPUs of the job: TargetP 2.0 in `targetp.sif` holds TensorFlow 1.7.0, which uses every CPU the process may run on and reads no thread variable. Before, a T1 job with 4 CPUs changed 7 of 261 TargetP rows (the study: SignalP 3 and TargetP 914 of 30,018 rows, at most 1e-06, PiperNET `reports/transxpress_upgrade/`). Results change: none. On Aurum, a T1 run with SignalP and TargetP gives the same files as `t1-rnaspades-signalp-targetp`, and a copy of it with 4 CPUs for the SignalP and TargetP jobs gives the same SignalP and TargetP rows. The T1 data are too small to show the SignalP effect (0 rows changed with 4 CPUs before the fix too); in a 4-CPU job, PyTorch in `signalp.sif` uses 4 threads without the variables and 1 with them. The shell blocks changed, so in an old run folder Snakemake lists the SignalP and TargetP jobs for a rerun; pass `--rerun-triggers mtime input params software-env` to continue it.
- Resource requests follow the thread count. Rule `fastqc` asks for `2048 + 512 × threads` MB (the fastqc launcher gives Java 512 MB per thread). Rule `trimmomatic_parallel` asks for `2048 + 256 × threads` MB and passes `-Xmx` (`mem_mb` − 1024 MB) to Trimmomatic; the bioconda wrapper otherwise sets a 1 GB heap, and 16 threads stop with a Java heap error (reproducibility study in PiperNET `reports/transxpress_upgrade/`, double-thread run; a run by hand with `-Xmx2g`, job 3308529, gave the same gzip bytes as 8 threads). At the default 8 threads both rules ask for the same memory as before. `trimmomatic_parallel` writes each output as `<index>.tmp.<part>.qtrim.fastq.gz`, tests it with `gzip -t` and then gives it its name (in a pilot run of the same study, one trimmed file had 126 broken bytes while Trimmomatic reported success). `kallisto_threads` defaults to 1: kallisto runs on 1 thread whatever the value, because `align_and_estimate_abundance.pl` passes no `-t` to it. Results change: none. The shell block of `trimmomatic_parallel` changed, so in an old run folder Snakemake lists the trimming jobs for a rerun; pass `--rerun-triggers mtime input params software-env` to continue it (merge `f9ffa6d`).
- CI job `t1-image` runs on `ubuntu-24.04`. On `ubuntu-latest` (Ubuntu 26.04) the Apptainer 1.5.2 package cannot install, because it needs `libfuse3-3`. Results change: none (CI only) (merge `a5c78d5`).
- `tests/allowed_diffs.tsv` has the line `results/expression/bowtie2_rsem/*` (mode `skip`), so `tests/compare_runs.py` accepts a run that holds the folder of rules `align_reads` and `IGV` and a run that does not. Results change: none (test tool only). The folder is not compared by the script (merge `5b8c8b1`).
- Rule `prepare_samples_for_IGV` asks for 16 GB (`mem_mb=16384`). `samtools sort --threads 4 -m 2G` holds 8 GB of buffers in its 4 threads, and 10 GB was not enough on piper09 (9 libraries; the `sacct` records and the job logs show out-of-memory kills of the sort jobs). Results change: none. This is a resource limit; the shell block is unchanged and no output depends on it (merge `27bdaaa`).
- `results/summary/run_info.txt` has the lines `pfam_md5`, `rfam_md5` and `sprot_md5`: the md5 of the database files the annotation read (merge `c3f100e`). Results change: only `run_info.txt`, by these three lines. Two runs on one database folder give equal lines.
- Rule `kallisto` passes the strand flag (`--rf-stranded` or `--fr-stranded`) to kallisto when `strand_specific` is not empty (merge `025f358`). Before, `align_and_estimate_abundance.pl` (Trinity 2.13.2 in the image; the same lines are in Trinity 2.15.2 and on its master) dropped the flag: it appends `kallisto_add_opts` to itself, not the flag. Results change: for a run with non-empty `strand_specific`, the outputs of rule `kallisto` (`results/expression/kallisto/` and the six `results/summary/expr_*` tables). A run with `strand_specific: ""` is unchanged.
